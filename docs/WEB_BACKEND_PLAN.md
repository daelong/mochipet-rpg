# Phase 2 이후의 서버 확장 계획

이 문서는 설계 계획입니다. **NestJS API, PostgreSQL, Prisma 스키마·마이그레이션, 인증, 동기화 서버는 아직 구현하지 않았습니다.** Phase 1은 DB 없이 플레이 가능한 로컬 웹게임입니다. 프런트엔드에 사용할 서버 비밀값도 없습니다.

## 코드 경계

- `packages/game-data`: 표시·밸런스 데이터를 공유합니다. 서버 배포 시 같은 버전을 명시적으로 사용합니다.
- `packages/shared`: 타입·입력 검증·오프라인 규칙이 있습니다. `GameCommand`, `ServerGamePort`는 향후 연결 지점이며 현재 네트워크 호출을 하지 않습니다.
- `apps/web`: 렌더링과 사용자 명령을 담당합니다. 온라인 전환 시 서버 상태를 TanStack Query로 관리하고, 로컬 엔진과 서버 권한 모드를 명시적으로 구분합니다.
- `apps/api`: 다음 단계에서 NestJS 모듈형 모놀리식으로 추가합니다. 계정·펫·경제·저장 모듈을 둡니다.
- `apps/game-server`: Phase 4에서 Colyseus 방·이동·전투 동기화를 추가합니다. 현재 실행 가능한 서버가 있는 것처럼 표시하지 않습니다.

## DB와 명령 처리

Prisma 스키마와 첫 마이그레이션은 실제 API 구현 시 함께 작성하고 PostgreSQL에서 검증합니다. 계획 모델은 User, GuestSession, Pet, InventoryEntry, LearnedSkill, PurchaseReceipt, RewardLedger, HuntSession입니다. 개인키·암호·실제 연결 문자열은 저장소에 넣지 않습니다. API별 `.env.example`은 필요한 변수가 확정되면 추가합니다.

구매는 사용자 소유 펫을 확인한 후 요청 ID와 사용자 ID의 고유 제약, 현재 가격·레벨·구매 한도 검증, 잔액 조건부 차감, 아이템 지급, 영수증 저장을 하나의 DB 트랜잭션으로 처리합니다. 재요청은 같은 결과를 돌려주고, 같은 요청 ID에 다른 내용이 오면 거부합니다. 동시 구매와 네트워크 재시도를 통합 테스트합니다.

사냥은 서버가 시작한 HuntSession과 서버 시계·시뮬레이션으로 처치와 보상을 확정합니다. 클라이언트가 보낸 코인, 레벨, 피해량, 처치 횟수, 로컬 저장의 해시를 보상 근거로 받아들이지 않습니다. 로컬 게스트 기록을 온라인 경제에 그대로 가져오는 임시 경로를 만들지 않습니다. 전환 정책을 별도로 결정해야 합니다.

## 계정과 시간

게스트는 레벨 1부터 서버에서 생성할 수 있어야 합니다. 계정 연결 시 소유권 확인과 충돌 정책을 명시하고, HttpOnly·Secure 쿠키 기반 세션 등 실제 인증 방식을 정합니다. 로그인·저장·구매에는 스키마 검증, 권한 확인, CSRF 방어, 요청 제한, 감사 기록을 적용합니다. 같은 계정을 두 기기에서 열었을 때 저장 revision 충돌을 검출합니다.

자리 비움 보상은 서버 시계와 마지막 확정 시각으로 계산하며, 시간·획득량 상한과 지급 원장을 함께 둡니다. 브라우저의 현재 시각·종료 시각은 권한 있는 근거가 아닙니다.

## 단계별 검증

1. Prisma 마이그레이션 적용·롤백 전략과 격리된 PostgreSQL 통합 테스트.
2. 게스트·계정 연결, 권한 위반·세션 만료·요청 제한 검사.
3. 동시 구매·같은 요청 재전송·보상 재전송에서 중복 지급이 없는지 확인.
4. 두 기기의 동기화·구버전 클라이언트·자리 비움 보상 경계 검사.
5. PWA와 Document Picture-in-Picture는 Phase 3, 실제 모바일 브라우저·접근성·성능 실측을 별도 수행.
6. Phase 4 온라인 월드 진입은 서버의 레벨 20 판정 이후에만 허용.
